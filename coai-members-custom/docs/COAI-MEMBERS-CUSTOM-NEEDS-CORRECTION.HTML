HIGH staff-newsletters.php — manager flow Manager branch sets $campaigns_gateway = $campaigns_url (no reauth=1), while the later section builds wp_login_url(... ) . '&reauth=1' but then does not use it. This creates inconsistent 2FA behavior and makes it hard to reason about where 2FA is triggered. It also makes “step-up” behavior differ between manager vs newsletter_manager/admin. Make a single rule:
  • If you want “step-up reauth” for managers only, ALWAYS link managers through wp_login_url($campaigns_url) . '&reauth=1'.
  • If you do NOT want that, then remove the unused gateway variables and let kiosk/2FA enforcement be the only gate.
HIGH coai-manager-fluentcrm-kiosk.php — kiosk step 2 Comment says “redirect them into FluentCRM”, but code redirects to /member-portal/ when they hit any non-FluentCRM admin page. This is a classic “why did it bounce me?” source. After reauth/2FA, WP can land on /wp-admin/ or index.php; your kiosk will immediately bounce to the portal, which can look like the login “failed” or that FluentCRM won’t open. Decide the intended behavior and align comment + redirect:
  • If intent is “never show wp-admin, go to portal”: update comment to match.
  • If intent is “go to FluentCRM after reauth”: redirect to admin_url('admin.php?page=fluentcrm-admin') (optionally keep coai_route if present).
MED staff-campagins.php filename + route Filename appears misspelled: staff-campagins.php. Also it links to admin.php?page=fluentcrm-admin#/email/campaigns which conflicts with your kiosk mapping that uses coai_route → #/campaigns. Typos cause loading/require issues. Route mismatch can land users in an unexpected FluentCRM subpage or break kiosk expectations. Rename file to staff-campaigns.php and standardize links: use admin_url('admin.php?page=fluentcrm-admin&coai_route=campaigns') and let kiosk step 6 set the hash.
MED staff-broadcasts.php login URL Login fallback points to /mike2025/ while other pages use /member-login/. Different login entry points can trigger different redirects/guards and create “it works on one page, not the other” behavior. Standardize to the same front-end login slug everywhere: $login = home_url('/member-login/');
MED admin-members.php — coai_staff_can fallback The file defines a fallback coai_staff_can() if not loaded. This can silently diverge from your “real” permission logic in core/mu-plugins. If a load order changes (or a file is renamed/off), permissions might still “work” but not match your intended security model. Move the fallback to a single MU helper file (e.g., 01-coai-core.php) and remove per-file fallbacks. At minimum, make the fallback log include a unique marker so you instantly know it’s running.
MED coai-auth-bridge.php — role assignment Auth bridge always set_role() based on wp_members.usergroup. That will overwrite any manually assigned WP-only roles unless blocked. If a user exists in WP and is given extra WP roles (or multiple roles), they can lose them on next login via bridge. If you want multi-role, consider:
  • Only set role on first-time shadow user creation.
  • Or only set role if current role is subscriber/member.
  • Or use add_role-style capability grants instead of overwriting.
LOW staff-newsletters.php — identity precedence Precedence is Admin → Manager → Newsletter Manager, so a user who has both manager + newsletter_manager will be labeled “manager” and get the manager branch. You already log a warning for dual-role users. But behavior could surprise you if you expected newsletter_manager branch. Pick a policy and enforce it:
  • Disallow dual-role (best), or
  • Prefer newsletter_manager over manager for newsletter center, or
  • Prefer manager (current) but document it.
LOW admin-members.php — COAI column casing You carefully map DB columns to exact casing ($col_map), then use $_POST['COAI_number'] as input. Works, but is fragile if you ever rename form field or change DB column casing. Standardize on one internal key: keep form field as COAI_number, but define $form_key = 'COAI_number' once and reuse.
NICE Docs & Debug Several files use different log markers and some do not include enough context (member_id, user_login, page). When something “sometimes” happens, missing context makes logs less useful. Standardize logs:
  • Prefix with file marker
  • Include user_login, roles, and key GET params (page, coai_route)
  • Use consistent tags: [COAI][KIOSK], [COAI][AUTH], etc.
